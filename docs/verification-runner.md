# Isolated Verification

npm, pnpm, Yarn, Python (requirements/Poetry/uv/Pipenv), Rust Cargo, Ruby/Bundler,
SDK-style .NET, Maven, Gradle, Go and PHP Composer verification run
in an ephemeral Azure Container Apps Job, not inside
the web or worker container. Configure `VERIFICATION_JOB_RESOURCE_ID` and
`VERIFICATION_PUBLIC_ORIGIN` on web and worker. Deploy `infra/verification.bicep`
with the existing Container Apps environment ID and starter principal IDs.
Apply database migration `007_verification_jobs.sql` before deploying web.

The job has no managed identity, production secrets, ingress or shared volumes.
It has 2 CPUs, 4 GiB memory and a 60-minute execution limit. The supervisor uses
a random 75-minute capability limited to one job's snapshot and report. Each
repository variant executes under a separate non-root UID with a sanitized
environment; source, output and production credentials are not shared between
variants. Public network access is required for package registries. This is not a
network-isolated or penetration-tested hostile-code sandbox; use a dedicated
environment and controlled egress before admitting untrusted external tenants.

## Compiled and PHP ecosystems

The supervisor installs only the toolchains a snapshot needs, as root and before
repository files are materialized. Every download is checked against a pinned
digest and installation stops on mismatch:

- .NET SDK 10.0.401 (SHA-512), plus older .NET runtimes or `global.json` SDKs
  through the dotnet-install script pinned to a commit and SHA-256.
- Eclipse Temurin JDK 8, 11, 17, 21 or 25 (SHA-256), selected from the declared
  Java level and Spring Boot generation of each variant.
- Maven 3.9.16 (SHA-512) when no Maven wrapper exists; Gradle 9.7.1 (SHA-256)
  when no Gradle wrapper exists. Repository wrappers run as the variant user.
- Go 1.27.1 (SHA-256); newer `go` directives use the checksum-database-verified
  Go toolchain download.
- PHP 5.6-8.5 from the signed packages.sury.org repository, whose keyring package
  is pinned by SHA-256; Composer 2.10.3 or 2.2.30 LTS for PHP older than 7.2.
- Rust uses rustup 1.28.2 with a pinned bootstrap SHA-256 and exact stable
  `rust-toolchain[.toml]` versions (default 1.90.0). Rustup verifies distribution
  checksums. Floating `stable`/`nightly` declarations are refused.

Per detected project and variant the matrix is:

| Ecosystem | Install/build | Tests | Dependency audit |
| --- | --- | --- | --- |
| .NET | `dotnet restore`, `dotnet build -c Release` for solutions or projects | `dotnet test` for every test project, TRX counted | `dotnet list package --vulnerable --include-transitive` on runtime projects |
| Maven | `mvn -DskipTests package` | `mvn test`, Surefire JUnit XML counted | `dependency:list` runtime scope queried against OSV |
| Gradle | `gradle assemble` | `gradle test`, JUnit XML counted | resolved `runtimeClasspath` queried against OSV |
| Go | `go mod download`, `go build ./...` | `go test -json ./...` events counted | `govulncheck` v1.8.0 (reachable vulnerabilities) |
| PHP | `composer install --no-scripts`, `php -l` for every project file | PHPUnit or Pest JUnit XML counted | `composer audit --locked --no-dev` |
| Rust | `cargo fetch --locked`, `cargo build --locked --workspace --all-targets` | `cargo test --locked --workspace`, aggregate harness counters counted | `cargo metadata --locked` registry dependencies queried against OSV |

A test step passes only when the tool exits successfully and its reports show
at least one executed test, no failures and no skipped tests. High, critical or
unrated findings block the candidate; the same findings in the baseline are
recorded as diagnostics only when the audit output is parsable. Tool errors
never become a pass. The server independently requires test counters as well as
the runner's successful exit status. Go and Composer candidates receive `go.mod`/`go.sum` and
`composer.lock` generated by the package manager in the job; model output cannot
write lockfiles. Cargo requires an original reviewed `Cargo.lock`, even for
libraries. Candidate locks are generated by Cargo as the candidate UID. Git,
custom-registry and external path dependencies have no qualified audit mapping
and fail closed; an empty registry inventory is valid only after real Cargo
metadata execution. Cargo test filters/ignored tests block approval.

## JavaScript package managers

The source manager owns its lock: npm uses `package-lock.json`, pnpm uses
`pnpm-lock.yaml`, and Yarn uses `yarn.lock`. pnpm and Yarn require an exact stable
`packageManager` declaration; the verifier never guesses their versions or
converts them to npm. Multiple competing locks, mismatched declared owners,
manager/version changes and incompatible Node engines are blocked. npm without
a declaration retains the verifier image's npm; an exact declared npm version
is installed and used. Root workspace scripts (including `pnpm-workspace.yaml`)
cover the workspace; absent scripts remain missing checks.

Before any repository file is materialized, known manager packages are downloaded
at the declared exact version from the npm registry, checked against published
SHA-512 SRI (and source-declared Corepack hash, when present), installed with scripts
disabled and engine checks enabled, and their executable version is verified.
Yarn Classic and modern CLI use their corresponding official packages. This is
registry integrity verification, not an independent publisher-signature audit.
Repository `yarnPath` is disabled; repository code/plugins, when used, execute
only as the unprivileged variant user.

Both variants perform frozen/immutable installation without lifecycle scripts,
the real build script, a nonempty unskipped test suite, and the manager's
production dependency audit. Vitest/Jest use bounded JSON reports; Node tests
use machine-readable TAP counters. pnpm/Yarn audit JSON must parse completely;
network errors and malformed output fail, not pass. Candidate lock updates use
the selected manager, are persisted before execution and remain part of the
reviewed changeset. Non-npm baseline locks are never regenerated by automatic
test-tooling overlays.

Ruby/Bundler has a real qualified Linux executor. CMake C/C++ and GnuCOBOL now
have real compilation, executable test and native dependency inventory/audit
adapters, but **passing native qualification remains incomplete** on the
current pinned Debian image: mandatory audits block the candidate. A JavaScript
pass cannot hide a native test or audit failure. No placeholder/no-op adapter
or missing audit exemption exists.

## Ruby and native executors

Tool installation runs before repository materialization. Signed Debian
packages are requested at exact versions: Ruby 3.1.2-7+deb12u1, CMake 3.25.1-1,
GnuCOBOL 3.1.2-5+b1, GCC/G++ 12.2.0-14+deb12u1 (meta packages 4:12.2.0-3),
Make 4.3-4.1 and binutils 2.40-2. Executable versions are checked. Bundler is
selected from the source lock's exact `BUNDLED WITH` version, downloaded from
RubyGems and verified against its published SHA-256 before installation.
Other declared Ruby interpreter versions remain blocked rather than silently
running on Ruby 3.1.2.

Ruby requires a reviewed `Gemfile.lock`. Both variants perform frozen Bundler
installation, syntax compilation, **every detected RSpec and Minitest suite**,
and a RubyGems OSV audit of the locked dependency inventory. RSpec JSON examples
and summary counters must agree; Minitest emits structured counters from its
real summary reporter. Empty, failed and pending/skipped suites fail. Git and
external path dependencies have no qualified audit mapping and fail closed;
the repository's own root gem is local application code, not a registry
dependency. Candidate lock updates use the same exact Bundler as the source.
Original manifests/locks and tests are not replaced with another manager.

CMake uses a fresh Release build directory, real compilation/linking and CTest
JUnit with `--no-tests=error`. Disabled/not-run testcase statuses count as
skips even when CTest exits zero. The native audit inventories compiler header
dependency files, linker traces and the shared libraries of fresh ELF build
artifacts, maps system paths to Debian source package versions, and queries
`Debian:12` OSV advisories. Unknown/unowned paths, unresolved libraries,
missing artifacts, incomplete OSV pages and high/critical/unrated findings
block approval. FetchContent, ExternalProject, custom process/download steps,
vendored dependencies, Conan, vcpkg, Meson and MSVC remain unqualified; their
locks/build mechanisms are not ignored or converted.

GnuCOBOL requires reviewed `tests/cobol-contracts.json`, for example:

```json
{
  "version": 1,
  "programs": [{"name": "contract", "sources": ["src/main.cob"], "format": "free"}],
  "tests": [{"name": "total", "program": "contract", "stdin": "", "stdout": "TOTAL=5\n", "stderr": "", "exitCode": 0}]
}
```

Every detected `.cob`, `.cbl` or `.cobol` source must belong to a declared
program; copybook directories are passed to the compiler. Omitted `format`
means fixed format. Every program needs executable assertions. The trusted
test driver runs the actual compiled programs as the variant UID and compares
stdout, stderr (empty by default) and exit status; each program invocation has
a 30-second limit. Skips/arbitrary test commands are forbidden. The manifest
is bounded to 100 KB, 8 programs and 64 tests. GnuCOBOL/shared-library inventory
receives the same mandatory Debian OSV audit, not an empty/no-op audit.

Native canary blockers on 2026-11-04 are concrete: glibc
`2.36-9+deb12u14`, GCC `12.2.0-14+deb12u1` and GnuCOBOL's transitive
libraries have unrated advisories. The CMake Linux-header inventory maps to
Linux `6.1.190-1`, whose first OSV page alone contains 1,000 advisories.
The adapter now follows bounded OSV pagination (up to 100 pages and 10,000
distinct advisories), rejects incomplete/repeating pages and retains every
finding. The previously recorded native canaries predate this pagination fix;
they are not retroactively declared passing. These findings are
**not waived**. Successful compilation/tests are not recorded as successful
overall native verification.

### Runtime canary evidence (2026-11-04)

Dedicated ephemeral job `modernize-runtime-40f315b8` in the authorized pilot
`rg-demo` used the pinned Node 22 verifier image, identity `None`, no production
secrets and an ownership tag. No existing verifier definition or app revision
was changed. Executions:

- `modernize-runtime-40f315b8-14xj0s3`: pnpm 10.28.2, Yarn Classic 1.22.22,
  Poetry 2.2.1, uv 0.9.9, Pipenv 2025.0.4 and Rust 1.90.0 passed both
  variants. Each profile separately rejected failing, empty and skipped suites.
  pnpm/Classic audits retained the deliberately vulnerable baseline `minimist`
  1.2.5 findings and rejected the candidate. A mixed six-project snapshot passed
  54 real command steps with 12 nonempty, unskipped test reports.
- `modernize-runtime-40f315b8-ev0ap4x`: Yarn 4.18.1 passed both variants and all
  negative test cases; its real vulnerability audit rejected `minimist` 1.2.5.
  Rust fetched/built locked `itoa` 1.0.15 and completed live OSV dependency
  queries, passed both test variants and rejected fail/empty/ignored cases.
  The combined Yarn/Rust snapshot passed 16 real command steps.

These are runner/toolchain canaries plus focused server-gate tests, not evidence
of a deployment, live source-provider onboarding, every manager release or
arbitrary applications passing. Follow-up execution
`modernize-runtime-40f315b8-h7yavcd` qualified Ruby 3.1.2/Bundler 2.6.9 with
both RSpec and Minitest (two tests per variant) and rejected failing, empty and
skipped suites. Its actual Ruby report passed the server's snapshot/evidence
gate. CMake and COBOL compiled and ran real tests, but their required native
audits blocked the candidate as described above; neither is advertised as a
passing qualified platform.

Cross-runtime manifest removal is allowed only for `rewrite` with an unchanged,
reviewed source acceptance manifest containing the same black-box contract
check on **both** variants. The contract must actually execute successfully
with nonempty/unskipped counters on the candidate as well as the baseline.
Original test sources (including inline Rust test modules) remain immutable.
Manager/version changes within a retained runtime are still forbidden; this
is not permission to convert pnpm/Poetry/Bundler locks to another manager.

Characterization tests for these ecosystems must contain `Characterization` in
their path. Only those are copied into the verification-only baseline so the
original application executes them too; tests for new behavior run on the
candidate only. Original test sources remain immutable. Rewrites across backend runtimes,
such as Java to Node.js, require the unchanged, reviewed cross-runtime contract
described above; unrelated baseline/candidate unit suites cannot establish parity.

## .NET Framework on Windows

Snapshots containing non-SDK project files, `net4x` target frameworks or
`packages.config` are verified in a per-job Windows container in Azure Container
Instances, because the original application builds and runs only on Windows.
The container uses `mcr.microsoft.com/dotnet/framework/sdk:4.8.1` pinned by
digest (MSBuild, NuGet, VSTest and .NET Framework targeting packs) and installs
the .NET 10 SDK (SHA-512) plus pinned runtimes when a variant uses SDK-style
projects. The supervisor script is downloaded through the same job capability.
It creates separate local accounts for baseline and candidate, restricts each
work tree to its account, proves before any repository command that the account
cannot see the capability token, and stops otherwise. Legacy variants use
`msbuild /t:Restore;Build` and `vstest.console` with TRX counting; SDK-style
variants use the same `dotnet` matrix as Linux. The audit queries OSV with
packages from `packages.config` and restored project assets. Evidence carries
the same command labels, so the server gate is unchanged. Container groups are
deleted after the final report and by the worker's recovery loop.

Copied `.NET` characterization test projects are retargeted to the framework of
the original project they reference (for example `net48`, with `LangVersion`
`latest`). The Windows verifier has an implemented, **not live-qualified**
.NET + npm execution path using the SHA-256-pinned
Node 22.23.4 Windows archive. npm install/build, Node TAP/Vitest/Jest test counting,
audit and dependency-lock preparation run under the variant's separate local
account. An explicitly declared npm version must match the installed exact
version. Mixed Windows repositories remain blocked at readiness and the live
supervisor: East US ACI failed with an infrastructure/containerd bridge error
before the script started, and Azure denied the alternative West Europe region.
No failed infrastructure probe is treated as an application pass. pnpm/Yarn and
Python/JVM/native projects also require Windows-specific adapters. Required modernization
scenario checks on Windows are also blocked until their executor is qualified.
The authorized Container Apps Job environment supports only `linux/amd64`
images ([Microsoft documentation](https://learn.microsoft.com/azure/container-apps/containers)).
A real mixed Windows qualification uses a separately authorized ephemeral
Windows ACI container group; no production app or existing verifier definition
is changed to work around that restriction. See the runbook for actual results;
local helper tests alone do not qualify the Windows runtime.

## Candidate static and credential scanning

New Linux verification jobs require a separate candidate scan using Semgrep
1.183.0, installed from its SHA-256-pinned Linux wheel before source is
materialized. Rules are local to the application; no repository source is sent
to an external scanning service, and metrics/version checks are disabled.
The scanner works on a fresh copy of the exact candidate snapshot, not mutable
build output. Repository ignore files cannot suppress the mandatory rules.

Rules cover selected dynamic evaluation, shell execution, unsafe copy and
disabled TLS patterns, plus high-confidence credential formats. Tool errors,
parse errors, incomplete structured results and findings block the candidate.
The server requires the scan step for snapshots requesting it; a plain exit
code without the expected structured evidence is insufficient.

Dedicated canary `modernize-security-40f315b8-nace6t7` executed the actual pinned
scanner: clean input passed, dynamic evaluation and credential fixtures failed,
and `.semgrepignore` could not hide the injected finding. This is a bounded
local rule set, not complete taint analysis, all-language security coverage or
hostile-code certification. Windows static scanning remains a separate release
qualification requirement; the Linux scanner is not reported as having run there.
ASP.NET Web Forms, WCF hosting and IIS behavior are covered only by executable
tests, not by browser or IIS automation. Pulling the Windows image can take
10–20 minutes when it is not cached on the Container Instances host.

Evidence: container group `mz-winverify-start-1790234580` verified a legacy
non-SDK `net48` project with `packages.config` against a `net10.0` candidate.
Baseline restore, build and tests passed on .NET Framework, as did the copied
characterization tests retargeted to `net48`. The candidate passed restore,
build, tests and audit. The baseline `Newtonsoft.Json` 12.0.1 finding
(GHSA-5crp-9r3c-p9vr, high) was retained as a diagnostic, giving the result
`passed`.

Source is fetched from the exact recorded commit, including binary blobs, and
the proposed changes are applied without creating a GitHub branch. Truncated
trees, symlinks, submodules, tracked credential files, more than 3000 files or
30 MB of source are rejected. GitHub/Foundry credentials stay in the dispatcher.

Every baseline JavaScript project must have its manager-owned lock before generation.
New or changed candidate manifests have their lockfile resolved with
`npm install --package-lock-only --ignore-scripts --no-fund` in the candidate's
unprivileged sandbox. Only bounded, user-owned regular lockfiles matching a
snapshot manifest are accepted; symlinks and source-code artifacts are rejected.
The server atomically persists candidate lockfiles, updates the changeset digest,
invalidates older reports and records an audit event before tests start. Human
approval therefore covers the resolved dependency changes too.

Explicit build/test scripts are
required for a passing result. If either script is absent or empty, the runner
executes the remaining available checks and records their logs, then reports
`unsupported` with the missing script names. Missing scripts never count as
passed checks; approval stays blocked. A baseline audit failure is retained while
candidate checks continue, so existing dependency findings do not hide candidate
results. A completed baseline audit reporting high/critical vulnerabilities is
diagnostic when candidate audit passes and all mandatory build/test commands pass
on both variants. Baseline audit timeouts, network failures and other errors still
block approval. Missing tests are never waived. Other command failures stop
execution and are recorded together with known missing prerequisites.
Workspaces use their root scripts. Vitest, Jest and Node TAP test reporters are
recognized; incompatible or counter-free test scripts fail explicitly.
No script or missing dependency is invented to make verification pass.

For a legacy source with no existing test command, a reviewed
`tests/baseline-harness.json` can record a baseline manifest, lockfile and the
Vitest/jsdom/Testing Library dependencies needed by the common suite. Only the
test command and allowlisted development dependencies may differ from the source
manifest. Existing runtime scripts and dependencies remain unchanged. The common
candidate tests are copied into the isolated baseline; existing baseline test
files cannot be overwritten. This overlay is a visible candidate file included
in the changeset digest. It does not modify the GitHub source branch. Its
dependency install and audit results are reported like other baseline checks.

For npm projects with no test command, the platform can also copy additive
candidate tests and allowlisted Vitest tooling into a baseline sandbox. Its
manifest retains the original runtime fields and existing dependency versions.
The baseline test-tooling lock is resolved separately and cannot change locked
runtime packages. It is not copied into the candidate or committed to GitHub.
An incompatible baseline test harness fails; it is never skipped to obtain a
passing candidate.

The Admin-only repair endpoint accepts version-locked dependency and test
integration files, binds their before-content to the pinned GitHub source and
records an audit event. It refuses active generation/verification and invalidates
old evidence. It never approves or publishes a proposal.

For both baseline and candidate, the supervisor executes:

1. `npm ci --ignore-scripts --no-fund`
2. `npm run build`
3. `npm test -- --run`
4. `npm audit --omit=dev --audit-level=high`

Each command is limited to four minutes, captures its exit code and the last
32,000 log characters, and terminates its process group on timeout. Dependency
install hooks are disabled; a project requiring them may need an explicitly
reviewed build strategy. Existing tests can be weak or misleading: passing
commands do not prove complete behavioral equivalence, correct architecture,
coverage, security or enterprise readiness.

Approval and publication require the latest passing report for the exact source
SHA and changeset digest. Edits make older reports stale. A successful report
does not publish anything: human approval is still required. The Verification tab
can start verification for existing blocked runs and displays command logs.
Generation requires a configured verifier and starts it automatically. Dispatches
with no report after ten minutes can be recovered by the worker, at most three
times per hour. Recovery invalidates the abandoned job capability and does not
replace active reports or touch approved runs. Failed checks still need repair;
recovery is not an automatic pass or automatic behavior exception.

Run processing uses a tenant/run advisory lock and per-attempt fencing token.
Cancellation and terminal-state checks precede candidate persistence. Refinements
and edits require stopped, unapproved runs, invalidate the old verification and
persist a pending request so queue delivery failure is recoverable. An ambiguous
Service Bus send leaves a saved run queued, not a misleading new-run failure.
Cancellation does not guarantee instantaneous cancellation of an external model
request; its late results must not be persisted.

The capability expires automatically. Snapshot payloads are removed after a
terminal report; expired payloads are cleared on a subsequent verification
request. Define an additional periodic retention policy for abandoned jobs and
execution reports according to organizational requirements.
